# v1.6.1 result — KHOA marine network diagnosis + NAVER map viewport fix

Two independent problems, fixed independently (v1.6.1 intentionally does not couple them).

## Part B — NAVER map viewport reset (root cause + fix)

### Root cause

`NaverMapProvider.update()` did two unrelated jobs in one call: redraw markers AND decide the
camera (`fitBounds`/`panTo`/`setZoom`). `PointMap.tsx` called it from a single `useEffect` whose
dependency list included `selectedId`, `previewId`, and `arbitrary` — state that changes on every
marker click, list-item click, and background map click. Any of those re-ran `update()`, and
`update()` unconditionally recomputed `fitBounds` (extent > 1) or `panTo`+`setZoom` (extent 1) from
scratch every time — overwriting whatever zoom/pan the user had set manually.

### Fix

Split the provider into two methods with an explicit contract:

- `syncMarkers(points, location, selectedId, previewId, arbitrary, onPreview)` — redraws markers
  only. Never calls `fitBounds`/`panTo`/`setZoom`. Safe to call on every state change.
- `frame(points, location)` — camera only (`fitBounds` if more than one coordinate, else
  `panTo`+`setZoom` for exactly one). Called only when there is a legitimate reason to reframe.

`PointMap.tsx` now has two effects:

```ts
useEffect(() => { provider.current?.syncMarkers(points, location, selectedId, previewId, arbitrary, ...) },
  [points, location, selectedId, previewId, arbitrary, state])
useEffect(() => { if (state === 'READY') provider.current?.frame(points, location) },
  [points, location, state])
```

The frame effect deliberately excludes `selectedId`/`previewId`/`arbitrary`. `points` only changes
when `LiveApp.tsx`'s `search()` sets a new catalog result (a real new search); `location` only
changes inside `locate()` (the explicit "현재 위치 사용" button) — both are legitimate reframe
triggers, and nothing else in the codebase sets either value, so no LiveApp.tsx change was needed to
achieve this — the existing state shape already matched the correct policy once the effect was split.

### Files changed

- `src/infrastructure/map/naver-map-provider.ts` — `update()` replaced by `syncMarkers()` + `frame()`.
- `src/features/point-discovery/PointMap.tsx` — one effect split into two, as above.
- `tests/unit/naver-map-provider.test.ts` — rewritten for the new API; added explicit "never touches
  the camera" assertions for marker sync and a dedicated `frame()` describe block.
- `e2e/live-map.spec.ts` — mock `Map` now counts `fitBounds`/`panTo`/`setZoom` calls
  (`data-fit-count`/`data-pan-count`/`data-zoom-count`); new test
  "user-driven viewport is preserved across preview, selection, and arbitrary map clicks" asserts the
  call count is unchanged across an official marker preview, a full point selection (data fetch +
  detail panel render), and an arbitrary background click.

### Viewport policy (final)

| Action | Viewport |
|---|---|
| New search result set (`points` changes) | may reframe (`fitBounds`/`panTo`+`zoom`) |
| Explicit "현재 위치 사용" (`location` changes) | may reframe |
| Official marker click / preview | unchanged |
| List-item preview click | unchanged |
| "이 포인트 선택" (selection + data fetch) | unchanged |
| Map background click (arbitrary marker) | unchanged |
| Nearest-candidate selection | unchanged |
| Detail panel / species guidance render | unchanged (no map-affecting state at all) |
| Mobile list/map switch, container resize | `setSize` only (unchanged existing behavior; resize was
  already not touching the camera before this fix — `ResizeObserver` only calls `setSize`) |

## Part A — KHOA marine network diagnosis

### Confirmed facts

Four requests, same param shape (`SDate/SHour/SMinute/EDate/EHour/EMinute/lat/lon/ResultType`),
compared:

| Path | Result |
|---|---|
| User's own PC → khoa.go.kr directly | HTTP 200, valid JSON (user-reported, already recorded in v1.6.1's prompt) |
| This session's sandbox → khoa.go.kr directly (`curl`, invalid `ServiceKey=test`) | HTTP 200, valid JSON body, headers carry **no** `Server: cloudflare` / `CF-RAY` — remote IP `211.57.32.7` (Korean range), i.e. a direct hit on KHOA's own origin, not fronted by Cloudflare for this path |
| Locally-run Worker code (`wrangler dev --local`, same source, dummy key) → khoa.go.kr | HTTP 502 `MALFORMED_RESPONSE` — meaning the upstream **fetch itself succeeded** (2xx), and only the schema check failed (expected: a dummy key returns an error-shaped body, not the success shape) |
| **Deployed** Cloudflare Worker (global edge) → khoa.go.kr, real `KHOA_MARINE_SERVICE_KEY` | HTTP 502 `UPSTREAM_ERROR`/`UPSTREAM_5XX` — upstream returned **HTTP 520**, with `Server: cloudflare` and a `CF-RAY` header present, `Content-Type: text/plain; charset=UTF-8` |

Three independent request paths that do **not** go through Cloudflare's global Workers edge (user's
PC, this sandbox's direct curl, and a locally-executed copy of the exact same Worker source) all
reach khoa.go.kr successfully at the transport level. Only the path that goes through Cloudflare's
deployed Workers edge gets a Cloudflare-branded `520` (a Cloudflare-generated code meaning "the
connection to the origin succeeded but the origin returned an invalid/empty HTTP response" — this is
Cloudflare's own error page, evidenced by `Server: cloudflare` and `CF-RAY`, not a KHOA application
error).

### What this rules out

- Not a code bug: identical source, run locally, transports fine.
- Not the credential: `/health` reports `marineReady: true`; the local dummy-key run got as far as a
  real HTTP response body (a schema mismatch, not a transport failure).
- Not a blanket "non-Korean network is blocked" policy: this sandbox's direct curl (its egress
  network is not Korean) succeeded with no Cloudflare interference at all.

### What remains a hypothesis, not a confirmed fact

The 520 is generated by *a* Cloudflare edge in the request path when Cloudflare's connection to
*some* origin fails or resets. Two distinct hypotheses remain open and this session could not
distinguish between them without access to KHOA's own infrastructure or Cloudflare account-level
traffic logs:

1. khoa.go.kr sits behind Cloudflare specifically for traffic that Cloudflare's own network
   classifies as coming from another Cloudflare tenant (a Workers subrequest carries recognizable
   network characteristics), and a WAF/firewall rule at that layer resets the connection —
   independent of the requester's own geography.
2. A transient KHOA-side or Cloudflare-side issue coincident with this session's testing window,
   unrelated to the requester's path.

Both are consistent with the evidence; neither is confirmed. "지리적(국가) IP 차단" specifically is
**not** supported by the evidence above (this session's own non-Korean-network curl succeeded) —
if anything, the discriminator observed is "did the request pass through Cloudflare's own Workers
egress," not "is the requester in Korea."

### Diagnostics added (safe, no secret/GPS/body exposure)

`worker/src/index.ts`'s `proxyUpstream` now logs, only on a non-2xx upstream response:
`host`, `httpClass`, `upstreamStatus`, `server` (response header), `cfRay`, `contentType`, `date`.
Never the `ServiceKey`, never the full upstream URL, never raw GPS, never the response body.

### Retry behavior

Unchanged — the marine route still does not retry inside the Worker (client-side `fetchWithRetry`
owns retry, per the existing v1.6 design). This diagnosis pass did not add retry-storm mitigation
because no additional retrying was introduced.

### Alternate proxy — research only, not built

Per the prompt's explicit instruction, an alternate backend is investigated only as research, and
only because the evidence above shows the current Worker's specific network path is the failing
element (not the code, not the credential). No infrastructure was created. Candidates that would meet
the stated constraints (server-side secret, no client-bundle exposure, HTTPS, CORS-controllable, low/
no cost) if the current Worker path turns out to be permanently blocked:

- A serverless function on a platform with a selectable Seoul region (e.g. Vercel Edge/Serverless
  Functions with `regions: ["icn1"]`, AWS Lambda in `ap-northeast-2`) — egress from a
  Korea-region IP rather than Cloudflare's global anycast, which may avoid whatever layer is
  generating the 520. Free tiers exist for both but require the user to create and authorize a new
  account/deployment — not done without explicit approval.
- Keeping the current Cloudflare Worker as the client-facing endpoint but having it call a second,
  Korea-region-hosted relay for this one route only — adds an extra hop and a second secret to manage,
  only worth doing if the current path is confirmed permanently blocked (not yet confirmed).

No infra created, no cost incurred, no account provisioned this pass.

### Final marine classification

**MARINE_WORKER_ROUTE_BLOCKED** — the code, contract, schema validation, and credential are all
confirmed working; the specific network path from the deployed Cloudflare Worker to khoa.go.kr is
the element that fails, isolated by three independent successful comparison paths. Root cause of
*why* Cloudflare's edge returns 520 on this specific path is not confirmed (see hypotheses above) —
reported as unconfirmed rather than asserted.
