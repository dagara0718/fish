## VERCEL_ESM_MODULE_RESOLUTION incident (continuation, 2026-09-18)

**Symptom**: `GET /api/health` on the deployed proxy (`https://marine-proxy-nu.vercel.app`) returned
HTTP 500 / `X-Vercel-Error: FUNCTION_INVOCATION_FAILED`, with the runtime log:
`Error [ERR_MODULE_NOT_FOUND]: Cannot find module '/var/task/api/_adapter' imported from
/var/task/api/health.js`. This happened before any KHOA call — purely a Node ESM module-resolution
failure in the deployed function.

**Root cause (two independent bugs, both needed fixing)**:

1. Every relative import in `marine-proxy`'s runtime files (`api/health.ts`, `api/marine-current.ts`,
   `api/_adapter.ts`, `src/index.ts`) was extensionless (`from './_adapter'`, `from '../src/index'`).
   TypeScript's `moduleResolution: bundler` accepts this at typecheck time, and Vitest's own resolver
   (vite-node) tolerates it too — but Vercel's Node.js Functions runtime does not bundle these files
   into one output; it transpiles each `.ts` file to `.js` 1:1 and ships them as separate files, then
   lets Node's real ESM loader resolve the `import` statements as written. Node's ESM loader requires
   an explicit extension on a relative specifier — `./_adapter` alone is not resolvable, even though
   `./_adapter.ts` exists on disk. **Vitest passing was not evidence this would work in production** —
   its resolver is deliberately more lenient than Node's real loader, which is exactly why the
   original test suite (24/24 green) never caught this.
2. Separately (not yet triggered by this failure, but latent): `worker/src/index.ts` and
   `marine-proxy/src/index.ts` both imported the shared marine validator from repo-root
   `shared/marine-response.ts`, which sits **outside** `marine-proxy/`'s Vercel Root Directory. Vercel
   only uploads/bundles files reachable from within the linked project's Root Directory
   (`marine-proxy/`, as set when the user ran `vercel link`) — a relative import that walks up and out
   of it (`../../shared/...`) is not part of the deployed bundle and would have failed the same way
   (`ERR_MODULE_NOT_FOUND`) the moment `api/marine-current.ts`'s import chain reached it, even after
   fixing (1).

**Fix**:

1. Added explicit `.js` specifiers to every relative import inside `marine-proxy`'s own runtime files
   (`./_adapter.js`, `../src/index.js`, `../shared/marine-response.js`). TypeScript's `bundler`
   resolution explicitly supports a `.js` specifier resolving to a `.ts` source file — this is the
   documented NodeNext-compatible authoring pattern, confirmed by `marine-proxy`'s own `typecheck`
   script staying clean after the change.
2. Relocated the shared marine validator from repo-root `shared/marine-response.ts` into
   `marine-proxy/shared/marine-response.ts` — inside the Vercel Root Directory, so it deploys as part
   of the same self-contained bundle. `worker/src/index.ts` (wrangler has no Root-Directory-style
   restriction; it bundles from the full repo checkout) now imports it via
   `'../../marine-proxy/shared/marine-response'` instead. The file's own tiny YYYYMMDD calendar-date
   check (`validDate`) was duplicated locally rather than importing `shared/fishing-api.ts` across the
   same boundary — a deliberate, small, documented exception: it is generic date-format validation,
   not KHOA marine contract logic, so duplicating it does not reintroduce the "two marine validators
   drifting" problem this file's relocation exists to prevent. The actual marine schema validator
   (`validateMarineResponse`) and the marine param-validation helpers remain a single canonical
   file, imported by both the Worker and the proxy — no drift.
3. Added `marine-proxy/scripts/esm-smoke.mjs` (wired as `npm run smoke`) — a regression guard that
   compiles the real entrypoints with the TypeScript compiler API (no bundling, matching Vercel's
   actual non-bundled shape) into a temp directory, then imports the compiled `.js` output through
   Node's real ESM loader. This is the check that would have caught the original bug before deploy:
   verified by temporarily reverting `api/health.ts`'s import back to extensionless and re-running —
   it failed with the exact same `Cannot find module '.../api/_adapter'` error the production log
   showed, then passed again once reverted back to the fix. `vitest`'s own test run was insufficient
   evidence, which is exactly why this separate check exists.

## Security / privacy

- **Secret**: `KHOA_MARINE_SERVICE_KEY` is read only from `process.env` inside the Vercel function; it
  is never in `marine-proxy`'s source, never in a committed file, never in a response body (redaction
  test passes), never logged. This report does not contain and did not request the key's value.
- **GPS**: `lat`/`lon` rounded to 3 decimal places before being placed in the upstream request URL;
  no server-side cache exists this PoC, so there is no cache-key exposure surface to check.
- **SSRF**: the upstream hostname/path (`https://khoa.go.kr/oceandata/api/tidalCurrentPoint/search.do`)
  is a source-code constant; no request parameter can influence host, path, or protocol — verified by
  the param allowlist rejecting any key outside the fixed `MARINE_PARAMS` set (test: "rejects
  invalid/duplicate/unknown params").
- **CORS**: same allowlisted-origin set as the Cloudflare Worker
  (`https://dagara0718.github.io`, `http://localhost:5173`, `http://127.0.0.1:5173`) — no wildcard.
- **Logging**: only `host`, `httpClass`, `upstreamStatus`, `elapsedMs`, `server`, `contentType`,
  `date` on a non-2xx upstream response — never the secret, never the upstream body, never exact GPS.
