# v1.3 product delta — map location selection → decision detail panel

Baseline: v1.2 (`8e2a5ba`, map-render fix `6810462`). This delta only extends the Live map/discovery
flow in `src/app/LiveApp.tsx`, `src/infrastructure/map/*`, `src/official-index/*`. It does not touch
the Demo fixture app (`src/app/App.tsx`), the Worker, or root `DESIGN.md`. No Provider boundary,
NAVER integration, or Demo/Live separation from v1.2 is rewritten.

## Product goal

Connect the map to the existing decision data: clicking an official point marker, an arbitrary map
location, or a GPS-ranked candidate all resolve, through explicit user confirmation, into one detail
panel answering: (1) is there evidence this location is open to fishing, (2) what is the current/
forecast environment, (3) which species have good official conditions, (4) what is the source and
as-of time, (5) what remains unconfirmed.

## New requirements

US8 — map location selection
- `REQ-FUNC-MAP-004`: NAVER map background click registers an `ARBITRARY_MAP_LOCATION`, distinct from
  `OFFICIAL_FISHING_INDEX_POINT`. A marker click never also fires a background click (time-guarded,
  independent of whether the SDK's event object supports `stopPropagation`).
- `REQ-FUNC-MAP-005`: an arbitrary location renders its own marker (`×` glyph, accessible label
  "선택 위치"), replacing any prior arbitrary marker — at most one at a time.
- `REQ-FUNC-MAP-006`: an arbitrary location resolves nearest official points from the full point
  catalog for the active fishing type (not the name-filtered search results), ranked by distance,
  capped at 5, ascending. Zero candidates renders "이 위치 주변에는 현재 공식 바다낚시지수 기준
  포인트가 없습니다." No point is auto-selected.
- `REQ-FUNC-MAP-007`: list ↔ map selection sync. A previewed point (from list, marker, or nearest-
  candidate confirm) is visually distinguished on its map marker; selecting from the list updates the
  map and vice versa. Marker vocabulary is fixed and never color-only: `◎ 현재 위치`, `● 공식 기준`,
  `◆ 선택`, `× 선택 위치`.
- `REQ-NFR-MAP-PERF-001`: an arbitrary map click only computes nearest candidates client-side; it
  never calls the official index API. The official index API is called only after explicit
  "이 포인트 선택" confirmation of an official point (preview → confirm stays two steps, unchanged
  from v1.2).

US9 — fishing access status (uncertainty-first)
- `REQ-FUNC-ACCESS-002` (extends the deferred `REQ-FUNC-ACCESS-001`): a selected point renders a
  "낚시 이용 상태" section with an explicit status: `ALLOWED_CONFIRMED`, `PROHIBITED_CONFIRMED`,
  `RESTRICTED`, `CHECK_REQUIRED`, `NO_EVIDENCE`, or `CONFLICT`. This status is a distinct model from
  `TrustStatus` (data freshness/collection) and from the official grade/score (fishing condition) —
  none of the three may be merged into one enum or one badge.
  This release ships one provider, `UnverifiedFishingAccessProvider`, which always returns
  `CHECK_REQUIRED` with empty evidence. No 낚시금지/출입통제 공식 API is connected in v1.3; see
  "Deferred sources" below. The absence of a prohibition record is never read as permission —
  `CHECK_REQUIRED` never displays as "가능", "문제없음", or "안전".
- `REQ-FUNC-ACCESS-003`: `FishingAccessProvider` is a typed boundary
  (`getAccessStatus(point): Promise<FishingAccessStatus>`) so a future regulator/port-authority
  source can be added without changing the detail panel's rendering contract.

US10 — species/environment detail presentation
- `REQ-FUNC-SPECIES-001`: the existing `OfficialSpeciesIndex[]` renders a top-of-panel "오늘 확인할
  어종" summary (species name + official grade only) above the full species grid. This is a plain
  rendering of already-fetched official data — not a probability, not a recommendation, not an AI
  inference. Copy never uses "추천", "확률", "잡힐".
- `REQ-FUNC-SPECIES-002` (documents existing v1.2 behavior, not new code): official grade/score come
  only from `totalIndex`/`lastScr` in the parsed response; no species is synthesized when the response
  has none.
- `REQ-NFR-DETAIL-001`: the detail panel exposes no internal identifiers (Requirement IDs, Task IDs,
  Provider/DTO type names, fixture QA vocabulary) in user-facing copy.

## Deferred sources (documented, not implemented)

No 낚시금지구역/항만 출입통제/보호구역/지자체 제한/군사·시설 통제 API is wired into this repository.
Candidate future sources for `FishingAccessProvider` implementations, to record and not build against
without the user's explicit go-ahead:
- 해양수산부 어업규제 공간정보 (연근해 특정해역, 수산자원보호구역) — data.go.kr, not yet reviewed for
  schema/coverage.
- 해양경찰청 항만시설 출입통제 공고 — no public structured API found during v1.2/v1.3 research;
  likely PDF/HTML notices only.
- 국방부/합참 사격장·군사시설 통제구역 — sensitive; any integration needs an explicit legal/security
  review before this repository touches it.
None of these are called, mocked, or stubbed with plausible-looking data in v1.3. `NO_EVIDENCE` and
`CHECK_REQUIRED` exist in the type so a real source can be added later without a status-model change.

## Explicit non-goals for v1.3

- `ENVIRONMENT_BASED_GUIDANCE` (temperature/current/season/tide/time → predicted species) is named in
  the domain type as a future `SpeciesGuidanceProvider` variant alongside `OFFICIAL_FISHING_INDEX`,
  but no `ENVIRONMENT_BASED_GUIDANCE` result is ever produced in this release. There is no model or
  rule set to back it; producing one now would be fabricated data.
- No reverse geocoding of arbitrary map clicks (no "인천 송도 앞바다"-style place description). The
  arbitrary location is presented as "지도에서 선택한 위치" without exposing raw coordinates in UI
  copy, matching the existing GPS privacy policy extended to map-click coordinates: client-state only,
  never persisted, never in the URL, never logged, never sent to the proxy except as the distance
  calculation input that stays in the browser.
