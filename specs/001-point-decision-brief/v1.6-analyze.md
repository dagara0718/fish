## Bug found and fixed during this pass

`KhoaTidalCurrentProvider.getCurrentObservations` originally checked `response.status === 503` on the
value `fetchWithRetry` returned, to detect the Worker's own `NOT_CONFIGURED` response and map it to
`MarineDataStatus: 'NOT_CONNECTED'`. But the shared `fetchWithRetry`/`classifyFailure` pair (reused
per REQ-FUNC-MARINE-006) treats every `503` as `RETRY` — correct for the fishing-index route's
transient-upstream semantics, but on the marine route a `503` means "key not configured," which is
permanent from the client's perspective. After retry exhaustion, `fetchWithRetry` always returns
`undefined`, discarding the final response object — so the `response.status === 503` branch was dead
code, unreachable in every real path. Caught by the unit test "returns NOT_CONNECTED on a 503,"
root-caused, fixed by threading the last-seen `httpClass` through the existing `onRetry` callback
parameter (no change to the shared helper itself) and branching on that instead of a response object
that no longer exists after exhaustion. Verified failing before the fix, passing after.

## GPS / secret handling

- Client: `KhoaTidalCurrentProvider` rounds `latitude`/`longitude` to 3 decimal places before either
  building the request URL or letting a caller derive a cache key — the exact GPS value never leaves
  the caller's stack frame beyond this provider's own `query` parameter, and is never logged (`log()`
  from `live-provider.ts` is not called by this provider at all — no observability event carries GPS).
- Worker: `handleMarineCurrent` independently re-rounds to 3dp server-side (defense in depth against a
  future caller that skips client-side rounding) before using the value in either the upstream request
  or the Cache-API key. `KHOA_MARINE_SERVICE_KEY` is read only from `env`, never logged, and the same
  text-scan redaction (`serialized.includes(secret) || ...encodeURIComponent(secret)`) used for the
  fishing-index route is reused verbatim for this route.
- No worker-side retry on this route (deliberate divergence from the fishing-index route, justified in
  `v1.6-product-delta.md` REQ-FUNC-MARINE-006's own text) — retry lives client-side only via
  `fetchWithRetry`, avoiding two independent retry layers multiplying attempts against KHOA.

## Trust/status-semantics separation check

`MarineDataStatus` (`SUCCESS`/`PARTIAL`/`STALE`/`UNAVAILABLE`/`UNSUPPORTED_AREA`/`NOT_CONNECTED`) is a
new, independent axis on `MarineCurrentResult` — it shares no field with `TrustStatus` (per-record
forecast freshness) or `CatalogStatus` (collection completeness). Each `MarineCurrentObservation` still
carries its own `trustStatus: TrustStatus` field separately. No code path merges these three axes into
one value or badge.
