# v1.5 product delta — live data resilience + species evidence hardening

Baseline: v1.4 (`0b513f1`). Two independent axes, no new features:

**A. Live data resilience** — a transient KHOA upstream failure on one page of a multi-page catalog
fetch must not discard already-collected pages, must not silently retry forever, and must not be
mislabeled as "no official data" or as a fresh/complete result when it is stale/partial.

**B. Species evidence hardening** — re-audit every `SpeciesProfile` numeric threshold against the
source-quality bar; a namu.wiki/news/hobbyist-fishing-site claim is never sufficient alone.

No ML model, no new recommendation algorithm, no real current-direction API connection, no 낚시금지구역
API, no UI redesign. NAVER map, the Worker's CORS/redirect/bound-fetch/secret-handling boundary, and
KHOA request/response parsing are unchanged in shape — this delta adds retry/cache logic around them,
not a rewrite.

## Problem model (precise, not "공식 데이터가 없다")

`LiveOfficialFishingIndexProvider.load()` fetches KHOA pages 1..N sequentially (N ≈ 6 for
totalCount≈1750, numOfRows=300) and threw immediately on the first `!response.ok`, discarding every
already-collected page. Confirmed live (2026-09-17): individual pages intermittently return 502
`UPSTREAM_ERROR` from KHOA while adjacent pages and single-point queries succeed seconds apart — this
is KHOA-side transient unreliability, not a Worker/rate-limit/auth defect (verified: `/health` 200,
single-page and single-point queries succeed reliably; the Worker's own 30 req/60s limiter returns a
distinct `RATE_LIMITED` body, never seen during these failures).

## Tradeoff decision: where resilience lives (§15 of the prompt)

Considered moving catalog pagination/aggregation into the Worker (a `/api/fishing-index/catalog`
endpoint that internally retries and aggregates). **Rejected for v1.5**: it multiplies the Worker's
surface (new endpoint, new response contract, new tests for the exact CORS/redirect/secret-scan
boundary already hardened twice this project) for a problem that is entirely observable and fixable
on the client, which already owns pagination. Implemented instead: retry + partial-preservation +
fresh/stale catalog cache inside `LiveOfficialFishingIndexProvider` (client-side), with the Worker
touched only additively (a `httpClass` field on its existing `UPSTREAM_ERROR` response body, for
client retry-classification and logging — no behavior change to any existing response). Revisit the
Worker-side aggregation only if client-side retry proves insufficient in practice.

## New requirements

US15 — retry and backoff (client-side, per KHOA page)
- `REQ-NFR-LIVE-RESILIENCE-001`: a page fetch that fails with a retryable outcome (network
  exception, timeout, HTTP 429/500/503/504, or HTTP 502 whose body is `{error:'UPSTREAM_ERROR'}`)
  retries up to 2 more times (3 attempts total) with bounded backoff (~250ms, ~750ms + jitter).
  HTTP 400/401/403/404/405 and 502 `{error:'MALFORMED_RESPONSE'}` never retry — retrying a parse
  failure or a config/request error cannot help.
- `REQ-NFR-LIVE-RESILIENCE-006`: retry is bounded per page (max 3 attempts) and only applies to
  pages that actually failed — a successful page is never re-fetched. Worst case for a 6-page catalog
  fetch with everything failing is 18 upstream calls, not routinely; the common case (0-1 failing
  pages) costs 0-2 extra calls.
- `REQ-NFR-GPS-PRIV-001` (carried over, re-verified): `AbortSignal` abort stops retry immediately —
  an aborted request is rethrown as an abort, never converted into `COLLECTION_FAILED` or retried.

US16 — partial and stale catalog
- `REQ-NFR-LIVE-RESILIENCE-002/003`: pages that succeed are preserved even if other pages in the same
  collection ultimately fail after retries. `getCatalog` returns `CatalogResult` with
  `status: 'PARTIAL'` and the points from the successful pages — never discarded, never silently
  merged into a false `'SUCCESS'`.
- `REQ-NFR-LIVE-RESILIENCE-004`: if a refresh cannot produce a complete catalog, a previously-cached
  **complete** catalog is preferred over a fresher-but-partial result (`status: 'STALE_FALLBACK'`).
  Only when no complete cache exists does a partial result surface to the caller.
- `REQ-NFR-CATALOG-003`: a partial refresh never overwrites the stored complete-catalog cache — the
  cache is written to only on a fully-complete collection.
- `REQ-NFR-LIVE-RESILIENCE-005`: `PARTIAL`/`STALE_FALLBACK` are rendered with distinct, honest UI
  copy — never presented as a complete, fresh result.
- Page 1 is special (it carries `totalCount`, so it decides `expectedPages` for the rest of the
  collection): if page 1 fails after retries, the whole collection is treated as failed for caching
  purposes and falls through to the same stale-cache-or-`COLLECTION_FAILED` decision as a total
  failure — an empty page-1 response is never treated as `SUCCESS` with zero points.

US17 — catalog caching and dedupe
- `REQ-NFR-CATALOG-001/002`: `getCatalog(fishingType)` returns a cached result with **zero** upstream
  calls when the cache is fresh (< 5 minutes old — matching the Worker's own page cache window). Past
  that window it attempts a refresh; the stale cache remains available as a fallback per
  REQ-NFR-LIVE-RESILIENCE-004. Cache key is `fishingType` only — never a coordinate, never GPS, never
  a credential.
- In-flight de-duplication: a second `getCatalog` call for the same `fishingType` while one is already
  running reuses the same in-flight promise rather than issuing a duplicate fetch sequence.

US18 — detail query resilience (same policy, not the same cache)
- `getOfficialIndex` (a single filtered page, used for the selected-point detail) goes through the
  same retry helper as catalog pages. Its existing per-point `STALE_CACHE` fallback (added in v1.3)
  is unchanged and is a **separate** cache from the catalog cache — a stale detail result for point A
  never leaks into point B's cache entry, and the catalog cache and detail cache are never confused
  with each other.

US19 — observability without secrets
- `REQ-NFR-OBSERVABILITY-001`: the client emits `console.debug` events
  (`catalog_fetch_started`/`catalog_page_retry`/`catalog_partial`/`catalog_stale_fallback`/
  `catalog_complete`) carrying only `fishingType`, `pageNumber`, `attempt`, `httpClass`, `elapsedMs` —
  never the service key, never a raw response body, never GPS. The Worker's existing `UPSTREAM_ERROR`
  response gains a `httpClass` field (`UPSTREAM_429`/`UPSTREAM_5XX`/`UPSTREAM_ERROR`) so the client
  can log/retry-classify without guessing from a bare status code; this is additive to the existing
  response shape and does not change any existing `error` value other tests already assert on.

US20 — species evidence hardening (no new requirement IDs beyond the evidence framework)
- `REQ-NFR-EVIDENCE-001`: `SpeciesEvidence.quality: EvidenceQuality` (`PRIMARY_GOVERNMENT` |
  `PEER_REVIEWED` | `ACADEMIC_INSTITUTION` | `SECONDARY` | `UNVERIFIED`) is tracked on every citation.
- `REQ-NFR-EVIDENCE-002`: a `SECONDARY`-only citation is never the sole basis for a `SpeciesProfile`
  numeric range or season window — see the v1.5 audit in `research/species-environment-evidence.md`.
- `REQ-NFR-EVIDENCE-003`: where no qualifying source exists, the factor field is absent
  (renders `UNKNOWN`) — never a guessed value, never a value kept "because nothing better was found."

## Consequence of the evidence audit (explicit, not hidden)

Only 참돔 retains a peer-reviewed/academic-backed `preferredWaterTemperature`/`toleratedWaterTemperature`/
`seasonalActiveMonths`. 우럭, 감성돔, 농어, 돌돔, 벵에돔 lose their v1.4 numeric thresholds (all were
sole-sourced from news/wiki/hobbyist sites) and now always resolve to `INSUFFICIENT_EVIDENCE`. This is
the explicit, intended, documented result of applying the stated evidence bar — not a defect to work
around by relaxing it. `profileVersion` bumped to `2026-09-v2` to mark the change.

## Cache/trust semantics note (§14 of the prompt)

`TrustStatus` (data collection/forecast freshness — `CONFIRMED`/`STALE`/`UNVERIFIED`/`CONFLICT`/
`COLLECTION_FAILED`) is unchanged and is **not** overloaded with catalog-cache freshness. Catalog
freshness is tracked separately as `CatalogResult.status`, which describes "how was this list of
points collected" (complete/partial/stale-cache-fallback/failed), a different axis from "is this
forecast record itself fresh" (`TrustStatus`, per-species/environment record). The two are never
merged into one field or one badge.
