## Bug found and fixed during this pass

The in-flight catalog dedupe (T083) initially keyed only on `fishingType`: a second `getCatalog` call
for the same type reused the first call's promise unconditionally. This meant aborting one search
(e.g., the user typing a new query) could abort the *shared* underlying fetch that a subsequent,
still-active search was also waiting on — corrupting a different caller's result, exactly the class
of bug §52 of the prompt warns about (though via dedupe-sharing rather than late-response overwrite).
Caught by an E2E test ("fast second search supersedes the first") failing on both projects, root-caused,
fixed by tracking each in-flight entry's originating signal and only reusing it if that signal is not
already aborted, and locked in with a dedicated unit test that fails without the fix (verified by
reverting the fix and re-running).

## Cache ↔ trust semantics

`CatalogResult.status` (SUCCESS/PARTIAL/STALE_FALLBACK/COLLECTION_FAILED — collection completeness) and
`TrustStatus` (CONFIRMED/STALE/UNVERIFIED/CONFLICT/COLLECTION_FAILED — per-record forecast freshness)
remain on separate types with no shared field. `EnvironmentBasedSpeciesGuidance.trustStatus` and
`OfficialSpeciesIndex.trustStatus` are untouched by this delta; only the catalog listing gained a new,
independent status axis.

## Partial ↔ UI

`LiveApp.tsx`'s `catalogNote(status)` prefixes — never replaces — the existing outcome message:
`PARTIAL` → "공식 포인트 일부만 불러왔습니다. ", `STALE_FALLBACK` → "최근 저장된 공식 포인트 정보를
표시합니다. ". Neither ever renders as if it were a complete, fresh result; `COLLECTION_FAILED` gets
its own distinct sentence, never reusing the SUCCESS copy path.

## Retry/rate-limit interaction

Retry is bounded at 3 attempts per page with short backoff (250ms/750ms + jitter); a 429 from the
Worker's own rate limiter is retried per the stated policy, but the short backoff window cannot
reliably clear the Worker's 60s sliding limiter — this is accepted (bounded, harmless, occasionally
helps if concurrent traffic clears the window) rather than engineered further, since the Worker's own
limiter is a distinct, already-tested boundary this delta does not touch.

## API key / secret / GPS

- No cache key (catalog: `fishingType`; detail: `officialPointId`) contains a coordinate, GPS value, or
  credential — asserted directly in `tests/unit/live-catalog-resilience.test.ts` "never uses a
  coordinate, GPS, or credential as the cache key".
- `console.debug` observability events carry only `fishingType`/`pageNumber`/`attempt`/`httpClass`/
  `elapsedMs` — no response body, no secret, no GPS (manual read of `log()`).
- Worker's `httpClass` addition carries only an HTTP status classification, never upstream response
  content or the service key — existing redaction tests (`worker/tests/proxy.test.ts` "redacts
  upstream errors") still pass unmodified.
